# G10 — Miếng kết thúc chunked (`0\r\n\r\n`) có tới không

Ngày đo: **2026-08-22** (giờ UTC ghi trong log, đo trong cùng phiên, cách nhau
vài giây)

Công cụ: `tools/measure_chunked_end.sh` (mới, script này), dùng
`curl --trace-ascii` để dump byte thật trên dây.

**Đính chính so với bản đo đầu** (review đã bắt lỗi): `-v` một mình KHÔNG in
byte khung chunked ra stderr — nó chỉ in header/metadata. Cờ `--raw` **không**
tắt việc đọc khung chunked; nó tắt "transfer decoding", nghĩa là khi chạy
`-v --raw -o file`, libcurl **giữ nguyên** byte khung chunked (kể cả
`0\r\n\r\n`) **ở cuối file body** thay vì tự giải mã/loại chúng đi — đã kiểm
lại bằng tay: `tail -c 40 file.bin | xxd` cho thấy đúng chuỗi hex
`30 0d 0a 0d 0a` ở cuối file khi dùng `-v --raw -o file`. Vậy lệnh mẫu ở task
file 2.1 (`curl -v --raw ... -o /dev/null`) **vẫn dùng được** — nó chỉ sai ở
chỗ đổ body (và terminator luôn) vào `/dev/null`; đổi `-o /dev/null` thành
`-o somefile` rồi soi đuôi file đó là thấy terminator, không cần đổi cờ nào.
Script này chọn `--trace-ascii` vì nó gom cả header, chunk-size và terminator
vào **một chỗ** dễ đọc trong cùng một lần chạy — không phải vì `-v --raw`
không làm được việc này.

Audio dùng: `warm_melodic.wav` (repo root, ~83 KB). Ảnh dùng:
`tests/fixtures/space_room.jpg`. Nội dung câu trả lời không quan trọng — G10 đo
khung giao thức, không đo nội dung.

### Hai chunk cuối cùng (raw, từ trace) — đây là bằng chứng chính

```
<= Recv data, 263 bytes (0x107)
0000: 100
0005: .......*.4..3........3.)......... ...9..........................
0045: ................................................................
0085: ................................................................
00c5: ................................................................
<= Recv data, 5 bytes (0x5)
0000: 0
0003:
== Info: Connection #0 to host localhost left intact
```

Khối cuối cùng là **đúng 5 byte**: byte 0 = ASCII `'0'` (chunk-size hex "0"),
byte 1–2 = `\r\n`, byte 3–4 = `\r\n` (trailer rỗng). Đây **chính là** khung kết
thúc chunked `0\r\n\r\n`. Ký tự `\r\n` không in được nên trace hiển thị trống,
nhưng vị trí offset (5 byte tổng, `0000: 0` rồi `0003:` trống) khớp chính xác
với cấu trúc 5-byte terminator, không khớp với bất kỳ chunk dữ liệu âm thanh
thật nào (chunk dữ liệu luôn có payload sau chunk-size, terminator thì không).

Ngay sau đó là `Connection #0 ... left intact` — libcurl chỉ báo dòng này khi
nó **tự xác định đã đọc đủ response** (đọc được terminator) và quyết định giữ
kết nối lại để tái dùng; nếu terminator không tới, curl phải đợi server đóng
TCP hoặc đợi hết `--max-time` rồi báo lỗi (exit code khác 0, thường là `28` =
timeout). Ở đây exit code là `0`, chạy hết `5s` — không phải do hết giờ.

## Kết luận

**Miếng kết thúc chunked `0\r\n\r\n` TỚI ở cả hai đường — localhost VÀ qua
Cloudflare tunnel.** Không có khác biệt giữa hai run: cùng cấu trúc 5-byte
terminator, cùng hành vi `Connection ... left intact`, cùng exit code `0`,
cùng chạy xong trong vài giây (5 s và 6 s) — không hề chạm ngưỡng
`BODY_GAP_MS` (30 s), ngưỡng header của board (90 s), hay ngưỡng 524 của
Cloudflare (100 s).

Theo bảng quyết định ở task file T02 mục 2.1:

> **Có tới** → README firmware sai → sửa README, đóng task, **không đụng
> server**.

Đây chính là trường hợp đó. **README firmware (và `HUONG_DAN_SERVER.md:167`)
mô tả sai thực tế hiện tại** của repo này: Starlette `StreamingResponse` +
uvicorn, đi thẳng và đi qua Cloudflare tunnel, đều phát ra terminator đúng
chuẩn. Cloudflare không đệm/nuốt nó.

**Việc cần làm tiếp** (thuộc wave sau, KHÔNG phải task này):
- Sửa README firmware và `HUONG_DAN_SERVER.md:167` — bỏ câu "board không đòi
  miếng kết thúc" / bỏ giả định phải dựa vào `BODY_GAP_MS = 30000` để biết hết.
- Cân nhắc: nếu board **thật sự** đang set `BODY_GAP_MS = 30000` và không đọc
  terminator (do bug ở phía firmware, không phải phía server), thì board vẫn
  tốn 30 giây chờ dù server đã gửi terminator đúng — đó là bug ở **firmware**,
  không phải server. Đo lại hành vi board thật (không phải curl) mới xác nhận
  được điều này; ngoài phạm vi G10 (G10 chỉ đo phía server/tunnel).

**Đây không rơi vào trường hợp "khác nhau giữa localhost và tunnel"** — cả hai
đều giống nhau, nên kết luận không đổ lỗi cho Cloudflare.

## Giới hạn của phép đo này

- Đo bằng `curl`, không phải bằng chính firmware ESP32. Nếu code phía board
  (không phải README của nó) có bug tự nó không đọc/tin miếng kết thúc dù nó
  tới đúng trên dây, thì G10 không phát hiện được — cần đo trên board thật hoặc
  đọc code `audio_player.cpp` / parser HTTP phía firmware (nằm ở repo firmware,
  ngoài phạm vi sửa của task này).
- Đo 1 lần mỗi đường (không lặp lại N lần để loại nhiễu mạng/route Cloudflare
  đổi PoP). Cấu trúc terminator ổn định và tường minh (5 byte, không mơ hồ) nên
  rủi ro do chạy 1 lần là thấp, nhưng nếu muốn chắc hơn có thể chạy lại
  `tools/measure_chunked_end.sh` vài lần.

## Đính chính sau review (không đổi kết luận G10)

Bản đo đầu tiên viết sai về cờ `-v --raw` của curl (xem đầu file). Đã kiểm lại
bằng tay trên localhost để chắc chắn trước khi sửa câu chữ:

```
$ curl -s -v --raw -X POST http://localhost:8000/process -H 'Expect:' \
       -F "audio=@warm_melodic.wav;type=audio/wav" \
       -F "image=@tests/fixtures/space_room.jpg;type=image/jpeg" \
       --max-time 30 -o /tmp/g10_verify_out.bin 2>/tmp/g10_verify_stderr.txt
$ tail -20 /tmp/g10_verify_stderr.txt      # không có byte khung chunked nào ở đây
$ tail -c 40 /tmp/g10_verify_out.bin | xxd
00000000: 0000 0000 0010 0000 0000 0000 0000 0000  ................
00000010: 0000 0010 0000 0000 0000 0000 0000 0000  ................
00000020: 000d 0a30 0d0a 0d0a                       ...0....
```

Đúng như review chỉ ra: `...0d 0a 30 0d 0a 0d 0a` ở cuối file body =
`\r\n0\r\n\r\n` — terminator nằm trong **file body** khi dùng `-v --raw -o file`,
không nằm trên stderr. Kết luận đầu bài (terminator arrives, giống nhau ở
localhost và tunnel) **không đổi** — chỉ câu giải thích về cờ curl được sửa lại
cho đúng.
